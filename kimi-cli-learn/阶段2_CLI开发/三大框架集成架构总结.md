## Click 框架作用位置

### 职责范围

```
命令行入口 (CLI Entry Point)
        ↓
Click 装饰器解析
        ↓
参数验证
        ↓
选项设置
        ↓
ShellApp 启动
        ↓
交互式会话开始
```

### 代码位置

**文件**：`src/kimi_cli/cli.py`

```python
@click.command()
@click.option('--work-dir', '-w', default='.', help='工作目录')
@click.option('--verbose', '-v', is_flag=True, help='详细输出')
@click.option('--ui', type=click.Choice(['shell', 'print']), default='shell')
def start(work_dir, verbose, ui):
    """启动 Kimi CLI 交互式 shell"""
    # Click 的职责：
    # 1. 解析 --work-dir、--verbose、--ui 参数
    # 2. 创建 ShellApp
    # 3. 运行交互式会话
    app = ShellApp(work_dir=work_dir, verbose=verbose, ui=ui)
    app.run()  # ← 交给 PromptToolkit
```

### 显示效果

```
$ kimi start --help

  启动 Kimi CLI 交互式 shell

Options:
  -w, --work-dir TEXT              工作目录
  -v, --verbose                    详细输出
  --ui [shell|print]               UI 模式
  --help                           显示帮助
```

## 完整数据流

### 从输入到输出的完整路径

```
┌────────────────────────────────────────────────────────────────────────┐
│                          用户交互流程                                   │
└────────────────────────────────────────────────────────────────────────┘

1️⃣ 命令行入口 (Click)
   ┌────────────────────────────────────────┐
   │ $ kimi start --work-dir /path          │
   │ $ kimi start --ui shell                │
   │ $ kimi --version                       │
   │ $ kimi --help                          │
   └────────────────────────────────────────┘
          ↓
   Click @click.command() 解析参数
   Click @click.option() 设置选项
          ↓

2️⃣ 交互式会话 (PromptToolkit)
   ┌────────────────────────────────────────┐
   │ ShellApp 启动                          │
   │ CustomPromptSession 初始化             │
   │                                        │
   │ seeback✨ >                            │
   │ (等待用户输入)                         │
   └────────────────────────────────────────┘
          ↓
   PromptSession.prompt_async()
   获取输入（实时补全、历史、快捷键）
          ↓
   解析 UserInput
   (mode, thinking, content, command)
          ↓

3️⃣ Agent 执行 (Soul + Wire)
   ┌────────────────────────────────────────┐
   │ Soul.run(user_input)                   │
   │                                        │
   │ Wire 监听事件流：                      │
   │  • StepBegin                           │
   │  • ContentPart (思考/文本)             │
   │  • ToolCall (工具调用)                 │
   │  • ToolCallPart (参数更新)             │
   │  • ToolResult (工具结果)               │
   │  • ApprovalRequest (批准请求)          │
   │  • StatusUpdate (状态更新)             │
   │  • StepEnd                             │
   └────────────────────────────────────────┘
          ↓

4️⃣ 实时显示 (Rich)
   ┌────────────────────────────────────────┐
   │ Rich Live 监听 Wire 消息               │
   │                                        │
   │ dispatch_wire_message(msg)             │
   │  ├─ ContentPart                        │
   │  │   └─ append_content()               │
   │  │       └─ _ContentBlock              │
   │  ├─ ToolCall                           │
   │  │   └─ append_tool_call()             │
   │  │       └─ _ToolCallBlock             │
   │  ├─ ApprovalRequest                    │
   │  │   └─ request_approval()             │
   │  │       └─ _ApprovalRequestPanel      │
   │  └─ StatusUpdate                       │
   │      └─ update_status()                │
   │          └─ _StatusBlock               │
   │                                        │
   │ compose() 合成所有组件                 │
   │ live.update() 刷新显示                 │
   │                                        │
   │ 屏幕显示最新状态（每秒刷新 10 次）    │
   └────────────────────────────────────────┘
          ↓

5️⃣ 回到交互层
   ┌────────────────────────────────────────┐
   │ Agent 完成                             │
   │ Live 自动清理（transient=True）        │
   │                                        │
   │ seeback✨ >                            │
   │ (等待下一个输入)                       │
   └────────────────────────────────────────┘
          ↓
   重复 2-5 步骤...
```

## 核心集成设计

### 三个框架的协作模式

```
┌────────────────────────────────────────────────────────────┐
│ 层级划分（职责清晰，解耦合）                                │
│                                                            │
│ Click 层          参数解析、启动程序                        │
│   ↓               (一次性工作)                              │
│                                                            │
│ PromptToolkit 层  交互式输入、命令处理                     │
│   ↓               (持续循环)                               │
│                                                            │
│ Rich 层           实时显示、美化输出                        │
│   ↓               (被动反应)                               │
│                                                            │
│ Soul 层           LLM 代理执行                             │
│ (不属于 CLI UI)   (业务逻辑)                               │
│                                                            │
└────────────────────────────────────────────────────────────┘
```

### 为什么需要三个框架？

#### Click 的作用
- ❌ 不适合做交互式会话
- ✅ 擅长参数解析和命令定义
- ✅ 提供自动帮助生成

#### PromptToolkit 的作用
- ❌ 不适合做美化输出
- ❌ 不适合参数解析
- ✅ 擅长交互式输入
- ✅ 提供补全、历史、快捷键

#### Rich 的作用
- ❌ 不适合接收用户输入
- ✅ 擅长实时流式显示
- ✅ 提供丰富的可视化组件
- ✅ 支持复杂的布局

### 数据结构流转

```
Click 层
  ↓
  command_args (参数字典)
  config (配置对象)

PromptToolkit 层
  ↓
  UserInput (用户输入)
    {
      mode: PromptMode,        # Agent / Shell
      thinking: bool,          # 思维开启/关闭
      command: str,            # 原始命令
      content: List[ContentPart]  # 富文本内容
    }

Soul 层（业务逻辑）
  ↓
  Wire 事件流
    [
      StepBegin,
      ContentPart(think=...),
      ToolCall(bash),
      ToolCallPart(arguments=...),
      ToolResult(...),
      StepEnd
    ]

Rich 层
  ↓
  屏幕显示
    💫 Thinking...
    ⟳ Using bash
    ✓ Used bash
    (result)
```

## 总结

### 设计原则

✅ **单一职责** - 每个框架只做一件事
✅ **职责清晰** - 界限明确，无重叠
✅ **易于维护** - 修改某一层不影响其他层
✅ **易于扩展** - 新功能可直接添加到相应层
✅ **高效协作** - 通过明确的接口和数据流协作

### 学习路径

```
1. 理解 Click   → 理解 CLI 参数和启动
2. 理解 PromptToolkit → 理解交互输入和状态
3. 理解 Rich    → 理解实时显示
4. 理解完整流程  → 理解三者的协作
5. 基于流程做修改  → 能自信地扩展功能
```

### 关键问题

**Q: 为什么不用 Click 的 Echo 输出？**
A: Click 的输出不支持实时更新，Rich 的 Live 支持每秒 10 次刷新。

**Q: 为什么不用 Click 的交互模块？**
A: Click 的交互能力有限（基本的 prompt、confirm），PromptToolkit 提供补全、历史、快捷键等高级功能。

**Q: 为什么不用 Curses？**
A: Curses 跨平台支持差，学习曲线陡峭。Rich 是纯 Python，易用性好。

**Q: 三个框架怎样兼容？**
A: 通过清晰的接口契约（UserInput, Wire 事件）和数据结构规范。
