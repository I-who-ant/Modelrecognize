## 🔢 为什么使用对数概率 (Log Probability)？

### 核心问题：数值稳定性

```
束搜索的目标:
  找到 y* = argmax P(y | x)
       y

其中:
  P(y | x) = P(y₁, y₂, ..., yₘ | x)
           = P(y₁|x) · P(y₂|x,y₁) · ... · P(yₘ|x,y₁,...,yₘ₋₁)

问题: 直接计算 P(y | x) 会导致数值下溢！
```

### 对比演示

#### ❌ 不推荐：直接使用概率

```
候选序列: "我爱你"
P("我爱你" | "I love you")
  = P("我" | <SOS>, c) × P("爱" | "我", c) × P("你" | "我 爱", c) × P("<EOS>" | "我爱你", c)
  = 0.6 × 0.8 × 0.7 × 0.9
  = 0.3024

候选序列: "我非常爱你"
P("我非常爱你" | "I love you")
  = P("我" | <SOS>, c) × P("非" | "我", c) × P("常" | "我 非", c) × ...
  = 0.6 × 0.4 × 0.3 × 0.2 × 0.8 × 0.7 × 0.9
  = 0.00607

问题显现:
  短序列概率: 0.3024
  长序列概率: 0.00607

当序列更长 (m=20):
  P ≈ 10^(-15) 到 10^(-30)
  → 计算机无法精确表示 (下溢为0!)
```

#### ✅ 推荐：使用对数概率

```
log P("我爱你" | "I love you")
  = log(0.6) + log(0.8) + log(0.7) + log(0.9)
  = -0.51 + (-0.22) + (-0.36) + (-0.11)
  = -1.20

log P("我非常爱你" | "I love you")
  = log(0.6) + log(0.4) + log(0.3) + log(0.2) + log(0.8) + log(0.7) + log(0.9)
  = -0.51 + (-0.92) + (-1.20) + (-1.61) + (-0.22) + (-0.36) + (-0.11)
  = -5.93

优势:
✅ 长序列仍然是有限数值: -5.93 (而非 0.0000001)
✅ 加法比乘法更稳定
✅ 计算机可以精确处理
✅ 便于数值计算和比较
```

### 数学原理

```
关键性质:
  log(a × b) = log(a) + log(b)

因此:
  log P(y | x) = log [P(y₁|x) · P(y₂|x,y₁) · ... · P(yₘ|x,y₁,...,yₘ₋₁)]
               = Σᵢ log P(yᵢ | x, y₁, ..., yᵢ₋₁)

束搜索使用对数概率:
  score = Σᵢ log P(yᵢ | x, y<ᵢ)

注意:
  - 分数是负数 (因为 log(P) < 0 当 0 < P < 1)
  - 更负 = 概率更小
  - 分数越大 (越接近0) = 概率越大
```

### 代码示例

```python
# ❌ 错误做法：直接使用概率
def bad_beam_search(probabilities):
    # 概率连乘，会导致下溢
    score = 1.0
    for p in probabilities:
        score *= p  # 概率越来越小，最终变为0！
    return score

# ✅ 正确做法：使用对数概率
def good_beam_search(log_probabilities):
    # 对数概率相加，数值稳定
    score = 0.0
    for log_p in log_probabilities:
        score += log_p  # 累加对数概率
    return score

# PyTorch 中的实际使用
log_probs = F.log_softmax(outputs, dim=-1)  # 直接获取对数概率
total_score = log_probs.sum()  # 对数概率相加
```

### 总结

```
❌ 避免: 直接使用 P(y | x)
  → 连乘导致数值下溢
  → 计算机无法处理极小值

✅ 推荐: 使用 log P(y | x)
  → 加法避免下溢
  → 数值稳定
  → 便于计算和比较

注意: 最终输出时，可以转换回概率
  P(y | x) = exp(log P(y | x))
```

## 📌 为什么需要优化束搜索？

### 基本束搜索的问题

```
问题 1: 偏向短序列
═══════════════════

束搜索默认最大化:
  score = Σᵢ log P(yᵢ | x, y<ᵢ)

问题:
  对数概率总是负数
  序列越长，累加越多负数
  → 系统偏向选择短序列！

实际示例:
───────

候选1: "我爱你" (3个词)
  score = -0.5 + (-0.2) + (-0.1) = -0.8

候选2: "我非常爱你" (4个词)
  score = -0.5 + (-0.3) + (-0.2) + (-0.15) = -1.15

候选3: "我非常非常爱你" (5个词)
  score = -0.5 + (-0.3) + (-0.3) + (-0.2) + (-0.15) = -1.45

结果: 系统选择最短的 "我爱你"
但 "我非常爱你" 平均概率更高!
```

```
问题 2: 重复生成
═════════════════

束搜索可能生成:
  "I love love love you"
  "我 爱 爱 爱 你"

原因:
  - 某些词的概率持续很高
  - 模型"卡住"在循环中
  - 没有机制防止重复
```

```
问题 3: 缺乏多样性
═════════════════

当 beam_size=3 时，所有候选可能很相似:
  候选1: "我 爱 你"
  候选2: "我 非常 爱 你"
  候选3: "我 真的 爱 你"

都是同一句话的变体，缺乏变化
```

## 🎯 束宽 (Beam Size) 的选择与权衡

### 什么是束宽 B？

```
束宽 (Beam Size) = k
═══════════════════

定义:
  在束搜索的每一步，同时保留 k 个最佳候选序列

作用:
  k 越大 → 搜索空间更大 → 质量更好
  k 越小 → 搜索空间更小 → 速度更快

k = 1: 等价于贪心搜索 (每步只选一个)
k = V: 等价于穷举搜索 (理论上)
k = 3-10: 实践中常用的平衡值
```

### 可视化示例

```
场景: beam_size = 3, 翻译 "I love you"

t=1: 生成第一个词
  候选1: [<SOS>, 我]     分数=-0.51  ✓ 选择
  候选2: [<SOS>, 你]     分数=-1.90  ✓ 选择
  候选3: [<SOS>, 爱]     分数=-2.30  ✓ 选择
  候选4-10000: 其他词    分数更低     ✗ 丢弃

t=2: 生成第二个词
  候选1扩展: [<SOS>, 我, 爱]   分数=-0.73  ✓ 选择
  候选1扩展: [<SOS>, 我, 喜欢] 分数=-2.81  ✓ 选择
  候选2扩展: [<SOS>, 你, 好]   分数=-2.59  ✓ 选择
  其他: 所有低分候选           ✗ 丢弃

结果: 每步始终只保留 top-3 个最佳候选!
```

### 超参数选择指南

```
不同任务的推荐束宽:
═══════════════════

机器翻译 (追求准确):
  k = 5-10
  原因: 需要精确匹配源语言语义
  代表: Google Translate, 百度翻译

文本摘要 (平衡质量与速度):
  k = 5-15
  原因: 需要选择最关键信息
  代表: 新闻摘要系统

对话生成 (追求多样性):
  k = 1-5
  原因: 希望有不同回复方式
  代表: ChatGPT, 小冰

代码生成 (追求精确):
  k = 3-7
  原因: 语法必须正确，不能有歧义
  代表: GitHub Copilot

诗歌生成 (追求创意):
  k = 1-3
  原因: 需要自由发挥，避免束缚
  代表: 文学创作辅助
```

### 束宽与性能的关系

```
性能对比 (WMT 2014 英译中):
═══════════════════════════

k=1 (贪心搜索):
  BLEU:  27.2
  速度:  10× (最快)
  内存:  1× (最少)

k=3:
  BLEU:  27.8
  速度:  5×  (较快)
  内存:  3×

k=5 (推荐):
  BLEU:  28.1
  速度:  1×  (基准)
  内存:  5×

k=10:
  BLEU:  28.3
  速度:  0.5× (较慢)
  内存:  10×

k=20:
  BLEU:  28.4
  速度:  0.2× (很慢)
  内存:  20×

结论:
  k=5 是质量与速度的最佳平衡点
  k>10 收益递减明显
```

### 实践建议

```
束宽选择流程:
═══════════

1. 先用 k=5 测试
   → 大多数任务的默认最佳值

2. 监控三个指标:
   - BLEU 分数 (质量)
   - 生成速度 (延迟)
   - 内存占用 (成本)

3. 根据需求调整:
   - 实时系统 → k=1-3
   - 离线翻译 → k=5-10
   - 高质量任务 → k=10-15

4. 观察趋势:
   - BLEU 提升 < 0.2 → 停止增大 k
   - 延迟不可接受 → 减小 k
   - 内存不足 → 减小 k

常见陷阱:
  ❌ k 越大越好 (实际: 收益递减)
  ❌ 所有任务用相同 k (实际: 任务相关)
  ❌ 只看 BLEU 分数 (实际: 需综合考虑)
```

### 束宽与多样性的关系

```
束搜索的固有局限性:
══════════════════════

即使 k=5，所有候选可能仍然相似:

示例:
  候选1: "我 爱 你"
  候选2: "我 非常 爱 你"
  候选3: "我 真的 爱 你"
  候选4: "我 特别 爱 你"
  候选5: "我 超 爱 你"

问题: 都是 "我...爱你" 的变体

解决: 引入多样性技术 (详见 22_2)
  - 温度采样 (Temperature Sampling)
  - 多样性束搜索 (Diverse Beam Search)
  - 随机采样 (Random Sampling)
```

### 代码中如何使用束宽

```python
# 创建束搜索解码器
beam_search = BeamSearch(
    model,
    beam_size=5,  # ⭐ 束宽 k=5
    max_len=50,
    sos_id=1,
    eos_id=2
)

# 束搜索内部工作原理
def beam_search_step(candidates, beam_size):
    """
    每一步保留 top-k 个最佳候选
    """
    all_candidates = []

    for seq, score, hidden in candidates:
        # 解码一步得到所有词的概率
        output, new_hidden = decoder(seq[-1], hidden)
        log_probs = F.log_softmax(output, dim=-1)

        # 保留前 beam_size 个词
        top_log_probs, top_indices = torch.topk(log_probs, beam_size)

        # 创建新候选
        for log_prob, word_id in zip(top_log_probs, top_indices):
            new_seq = seq + [word_id]
            new_score = score + log_prob
            all_candidates.append((new_seq, new_score, new_hidden))

    # 按分数排序，只保留 top-k 个
    all_candidates.sort(key=lambda x: x[1], reverse=True)
    return all_candidates[:beam_size]  # ⭐ 核心: top-k 剪枝
```

### 总结

```
束宽 k 的关键要点:
═════════════════

1. 核心概念
   - 每步保留 k 个最佳候选
   - k 越大质量越好但速度越慢

2. 推荐设置
   - 通用任务: k = 5
   - 实时系统: k = 1-3
   - 高质量任务: k = 10-15

3. 权衡考虑
   - BLEU 分数 vs 生成速度
   - 质量 vs 计算成本
   - 准确率 vs 多样性

4. 实践建议
   - 从 k=5 开始测试
   - 监控质量和性能指标
   - 根据任务调整

5. 局限与补充
   - 束搜索可能导致候选相似
   - 需要配合多样性技术使用
   - 详见: [22_2_束搜索优化](./22_2_束搜索优化.md)
```
