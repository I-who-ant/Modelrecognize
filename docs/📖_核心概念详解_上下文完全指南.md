## 1️⃣ 什么是上下文(Context)?

### 简单定义

```
上下文 = LLM能够"看到"的所有信息的总和

包括:
┌─────────────────────────────┐
│ 1. 用户当前输入的问题       │  ← 即时输入
│ 2. 之前的对话历史           │  ← 历史记录
│ 3. 你提供的背景信息         │  ← 参考资料
│ 4. LLM的训练知识(内部)      │  ← 模型知识
└─────────────────────────────┘
```

### 类比理解

```
把LLM想象成一个人在做题:

❌ 没有上下文:
   "这个问题问什么?"
   你的大脑一片空白,完全不知道说什么

✅ 有充足上下文:
   "根据之前讲的XXX理论,现在问你YYY问题"
   你立即明白了整个场景,能给出高质量答案
```

## 2️⃣ 上下文的三个层面

### 层面1: 对话历史上下文 (Conversation Context)

**含义**: LLM能看到之前说过的所有内容

**例子**:
```
用户: "Python有什么优点?"
LLM: "Python的优点包括..."

用户: "那用它怎么爬虫?"
LLM: 会记得前面说的Python,知道你是在问Python爬虫

✅ 对话历史上下文让LLM理解你的连贯问题
```

**你能做什么**:
- 在同一个对话中多次追问,LLM会记住前面的内容
- 如果LLM忘了,你可以重新提醒它

**示例代码**:
```python
# 不好的做法: 每次都重复背景
用户消息1: "根据用户反馈,我需要优化搜索..."
用户消息2: "搜索功能改进后,现在怎样..."

# ✅ 好的做法: 在一个对话中逐步深入
用户消息1: "我要优化搜索功能"
用户消息2: "用什么算法?" (LLM记得前面的背景)
用户消息3: "代码怎么写?" (LLM还是记得背景)
```

---

### 层面2: 提示词上下文 (Prompt Context)

**含义**: 你在提示词中明确提供的背景信息

**例子**:
```
⭐ 对比示例:

❌ 差的提示词 (上下文不足):
   "帮我翻译这句话: 'The quick brown fox'"

✅ 好的提示词 (上下文充足):
   "你是一个专业翻译，特别擅长自然科学领域的翻译。
   请将以下英文句子翻译成中文，
   保留专业术语的准确性：
   'The quick brown fox'"
```

**对比分析**:

| 提示词 | 上下文 | LLM的反应 |
|--------|--------|---------|
| ❌ "翻译: xxx" | 很少 | 可能用错术语 |
| ✅ "专业翻译，自然科学领域的，翻译: xxx" | 充足 | 准确理解你的需求 |

**你能做什么**:
- 在提示词中提供更多背景信息
- 说明你的身份/角色/目标
- 给出具体的约束条件

**最佳实践**:
```python
# 5部分结构(来自Day26_1的提示词模板)

# 第1部分: 角色定义(你是谁?)
你是一个专业的Python开发者

# 第2部分: 背景信息(发生了什么?)
我在开发一个数据处理系统

# 第3部分: 当前任务(现在要干什么?)
需要编写一个函数来清洗数据

# 第4部分: 具体约束(什么限制?)
只能用pandas库,不能用其他库

# 第5部分: 输出要求(怎样回答?)
给完整的可运行代码,包含docstring

这样LLM就有了充足的上下文!
```

---

### 层面3: 系统上下文 (System Context)

**含义**: 通过系统提示词设定的基本角色和行为

**例子**:
```
系统提示词: "你是一个温暖友好的AI助手,
           回答时总是以简单易懂的方式说明,
           如果不确定就说'我不知道'"

这就是系统级的上下文!
用户的所有问题都会在这个背景下被回答。
```

**对比**:
```
不同的系统上下文 → 完全不同的回答风格

用户问: "机器学习是什么?"

系统上下文1: "你是大学教授"
  回答: "机器学习是统计学和计算机科学的交集..."

系统上下文2: "你是个5岁小孩"
  回答: "机器学习就像教电脑学会做事情,
       就像你学会识别狗和猫一样!"
```

## 3️⃣ 上下文的大小和限制

### Token 限制 (最关键!)

```
什么是Token?
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
Token = LLM理解的最小单位(通常是一个词或几个字)

计算方式:
  英文: 平均 1 Token = 4 个字母
  中文: 平均 1 Token = 1-2 个汉字
  代码: 平均 1 Token = 1 个符号或单词
```

### 上下文窗口限制

```
不同模型的上下文限制:

模型                   上下文窗口      相当于字数
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
ChatGPT-3.5            4,096 tokens   约2万字
ChatGPT-4              8,192 tokens   约4万字
Claude 2               100,000 tokens 约50万字
Claude 3 Opus         200,000 tokens 约100万字
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

上下文消耗:
  你的提示词        占用 X tokens
  用户问题          占用 Y tokens
  对话历史          占用 Z tokens
  ────────────────
  总消耗 = X+Y+Z

  必须 < 模型上下文窗口!
```

### 实际影响

```
上下文充足:
  ✅ LLM能看到所有相关信息
  ✅ 回答更准确更详细
  ✅ 理解你的意图
  ✅ 给出高质量输出

上下文不足:
  ❌ LLM遗漏关键信息
  ❌ 给出不准确的回答
  ❌ 误解你的问题
  ❌ 需要多轮沟通才能说清楚
```

## 4️⃣ 如何充分利用上下文? (实践技巧)

### 技巧1: 明确提供背景信息

```python
❌ 不好的做法:
   Q: "怎么优化这段代码?"
   (LLM: 不知道你的代码是什么,只能猜)

✅ 好的做法:
   Q: "我有一个数据处理函数,处理100万行数据,
       现在很慢。这是代码:[代码]
       背景: 使用pandas处理CSV文件。
       怎么优化?"
   (LLM: 明白了背景,能给出针对性优化)
```

### 技巧2: 分步提问而不是一次性问完

```python
# ❌ 一次性问完 (不聚焦)
Q: "怎么用Python写一个完整的爬虫系统？
   包括网页获取、数据解析、数据存储、
   错误处理、代理轮换、反爬虫对策..."

(LLM的上下文被分散在太多细节上)

# ✅ 分步聚焦提问
Q1: "怎么用Selenium获取动态网页?"
(LLM: 完整的上下文聚焦在"动态网页获取")

Q2: "获取后的HTML怎么解析?"
(LLM: 前面说过Selenium,继续基于这个上下文)

Q3: "怎么处理爬虫被反爬虫的问题?"
(LLM: 记得前面的内容,给出针对性方案)
```

### 技巧3: 引用前面的对话

```python
Q1: "Python列表和元组的区别?"
A1: [LLM给出了对比]

Q2: "那怎么在函数中使用[对话1中提到的]元组?"
     ↑ 直接引用前面的内容,确保上下文清晰
```

### 技巧4: 给出充足的示例

```python
❌ 上下文不足:
   "帮我生成一些问答数据"
   (LLM: 不知道你想要什么样的问答)

✅ 上下文充足:
   "帮我生成Python教学的问答数据,
   格式如下(示例):
   {
     'Q': '列表和元组有什么区别?',
     'A': '列表是可变的,元组是不可变的...',
     'difficulty': 'beginner'
   }

   需要200个这样的问答对"
   (LLM: 完全明白了你想要什么)
```

## 5️⃣ 上下文中的常见问题和解决

### 问题1: "LLM好像忘了前面说的"

```
原因: 对话太长,超过了上下文限制

解决方案:
✅ 方案A: 总结一下核心信息
   "回顾一下,我们讨论的是[XYZ],
    现在要继续解决[ABC]的问题"

✅ 方案B: 开启新对话
   如果对话很长,可以开启新的对话,
   在开始时说:"之前我们讨论了XXX系统,
   现在要在此基础上做YYY"

✅ 方案C: 定期总结
   每10-15条消息总结一次关键信息
```

### 问题2: "上下文太长,响应变慢"

```
原因: Token数超多,LLM处理时间长

解决方案:
✅ 方案A: 清理不必要的历史
   删除不相关的对话,保留核心内容

✅ 方案B: 使用摘要
   把长的对话历史总结成关键要点

✅ 方案C: 切割对话
   分成多个较短的对话,而不是一个超长对话
```

### 问题3: "同样的问题,同样的提示词,答案不同"

```
可能的原因:
  ① 上下文不同 (前面问过不同的问题)
  ② 对话长度不同 (长对话中LLM可能注意力分散)
  ③ Token使用不同 (接近限制时会有变化)

解决方案:
  ✅ 新对话中重复同样的问题测试
  ✅ 添加"保证一致性"的指令
  ✅ 固定系统提示词
```

## 6️⃣ 上下文与Prompt Engineering的关系

### 上下文是提示工程的基础

```
提示工程的5层金字塔:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
        第5层: 高级技巧(ReAct/ToT/等)

        第4层: 迭代优化(多轮对话改进)

        第3层: 结构化提示词(5部分结构)

        第2层: 充分的上下文(背景信息)

        第1层: 清晰的需求描述
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

✅ 基础扎实(好的上下文)
   → 高层技巧才有效果

❌ 基础不足(缺少上下文)
   → 即使用高级技巧也白搭
```

### 具体例子

```
例子: 生成代码

❌ 没有充分上下文:
   提示词: "用Python写排序算法"
   结果: LLM随便写一个冒泡排序

✅ 充分上下文:
   提示词: "你是一个算法教师,
          要为学生讲解排序。
          背景: 学生已学过基础Python,
          但不理解快速排序的原理。
          现在要生成一个代码示例,
          包含详细的注释和逐步说明,
          帮助学生理解快速排序。"
   结果: LLM生成高质量的教学代码
```

## 7️⃣ 实战应用: 如何设计好的上下文

### 检查清单

```
在发送提示词前,问自己这些问题:

□ 我清楚说明了角色吗?
  "你是一个[角色]"

□ 我说明了背景吗?
  "在[情境]的背景下"

□ 我明确了当前任务吗?
  "现在需要[具体任务]"

□ 我给出了足够的例子吗?
  "例子: [示例1] [示例2]"

□ 我说明了约束条件吗?
  "限制条件: [约束1] [约束2]"

□ 我明确了输出格式吗?
  "输出格式: [格式说明]"

如果都是✅,那上下文就充分了!
```

### 三个等级

```
等级1: 最小上下文 (只有问题本身)
Q: "怎么快速排序?"
→ 可以工作,但可能不准确

等级2: 足够上下文 (有角色+背景+任务)
Q: "你是一个Python教师。
   我正在教学生快速排序。
   给我一个代码示例,
   包含注释和讲解。"
→ 回答会很好

等级3: 充分上下文 (包含所有细节)
Q: "你是一个Python教师,
   教授'数据结构和算法'课程。
   现在要为大一学生讲解快速排序。
   学生已掌握: 基础排序、递归、分治思想。
   目标: 让他们理解快速排序的原理。
   给一个代码示例,
   包含:
   - 详细的中文注释
   - 逐步的代码演进(简单→复杂)
   - 时间复杂度分析
   格式: Python代码块"
→ 回答会非常优秀
```

## 8️⃣ 常见错误和纠正

### 错误1: 认为上下文越多越好

```
❌ 错误想法:
   "我把所有信息都告诉LLM,
    这样上下文越充分越好"

✓ 正确理解:
   "上下文要充分且相关"

   例如:
   问: "怎么用Python爬虫?"
   ❌ 我把我的整个项目源码都复制进去
   ✅ 我只提供最相关的部分代码和背景

   → 相关的上下文 > 无关的大量信息
```

### 错误2: 忽视上下文窗口限制

```
❌ 错误做法:
   "我在一个对话里问了1000个问题,
    为什么LLM开始给出垃圾回答?"

✓ 正确理解:
   上下文有限制,必须注意

   解决方案:
   ✅ 监控消息数量
   ✅ 定期开启新对话
   ✅ 删除不必要的历史
```

### 错误3: 提供矛盾的上下文

```
❌ 错误例子:
   "你是一个严肃的学术助手。
    但也要用很casual的方式回答。
    还要用专业术语。"
   (这些要求互相矛盾!)

✓ 正确做法:
   "你是一个学术助手,
    用简洁清晰的语言解释复杂概念,
    同时保留关键的专业术语。"
   (要求一致且明确)
```

## 9️⃣ 总结: 上下文的黄金法则

```
黄金法则 (必须记住!):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1️⃣ 上下文 = LLM的"视野"
   上下文充分 → LLM看得清楚 → 回答准确
   上下文不足 → LLM瞎猜 → 回答垃圾

2️⃣ 上下文包括三层面
   对话历史 (前面说过的)
   提示词 (现在说的)
   系统设定 (基本角色)

3️⃣ 充分上下文需要5部分
   ✅ 角色定义
   ✅ 背景信息
   ✅ 当前任务
   ✅ 具体例子
   ✅ 输出要求

4️⃣ 要注意Token限制
   上下文太长 → 超过限制 → 出错
   定期检查消耗的tokens

5️⃣ 相关 > 数量
   100条相关信息 > 1000条无关信息
   删除干扰信息,保留核心内容

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

## 🔟 实战例子: 对比学习

### 例子1: 生成数据(来自Day23)

```python
❌ 上下文不足:
   Q: "生成一些问答数据"

   LLM: "不知道你要什么样的数据,随便生成了一些"

✅ 上下文充分:
   Q: "你是一个数据生成专家。
       我正在构建一个'Python教学'的知识库。

       背景: 这是给大学一年级学生的教学数据。

       任务: 生成50个高质量的问答对。

       具体要求:
       - 问题覆盖: 基础语法, 数据结构, 函数
       - 难度分布: 初级50%, 中级40%, 高级10%
       - 答案长度: 150-300字
       - 格式: JSON格式

       示例:
       {
         'question': '什么是Python列表?',
         'answer': '列表是Python中的可变序列...',
         'difficulty': 'beginner'
       }

       现在生成数据"

   LLM: 准确理解需求,生成高质量数据
```

### 例子2: 代码生成(来自Day26)

```python
❌ 上下文不足:
   Q: "写一个快速排序函数"

   LLM: 写了最基础的版本

✅ 上下文充分:
   Q: "你是一个资深Python开发者。

       背景: 我在开发一个数据处理系统,
            需要对大型数据集进行排序。

       任务: 实现一个高效的快速排序函数。

       具体要求:
       - 支持自定义比较函数
       - 需要处理重复元素的情况
       - 要有完整的错误处理
       - 包含详细的docstring和类型提示
       - 要有单元测试代码

       约束:
       - 只能用Python标准库
       - 时间复杂度必须是O(n log n)
       - 空间复杂度不能超过O(n)

       输出: 完整的可运行代码"

   LLM: 生成企业级的高质量代码
```
